# Card Builder 项目客观审计报告

审计日期：2026-08-11
审计范围：产品理念、产品定位、功能设计、UI、UX、可访问性、代码架构、数据与素材治理、部署状态、继续投入决策
方法：代码知识图谱、静态代码检查、桌面端与 390×844 移动端浏览器实测、关键交互回归、GitHub/部署只读核验、同类产品与官方权利条款核对

## 1. 结论先行

**建议继续，但应把它定义为“有截止期限的旗舰作品集项目”，不建议现阶段继续按商业产品无限扩功能。**

- 作为作品集：**8.2 / 10，值得继续 1–2 个收敛迭代。** 它已经能够展示原生 Web、Canvas、Three.js、复杂视觉系统、本地数据、服务端 API 与部署能力，辨识度明显高于普通 CRUD 项目。
- 作为面向陌生用户的创作工具：**6.7 / 10。** 核心链路可用且已由主流程浏览器回归覆盖，但功能密度、首次学习成本和真实用户验证仍会限制稳定增长。
- 作为可商业化的 NBA 球星卡产品：**5.1 / 10，当前不应追加重投入。** 最大问题不是视觉，而是目标用户和付费场景尚未验证，同时真实球员、球队 Logo、照片和签名带来较高授权成本与公开使用风险。

最理性的方向是：**冻结新特效与新卡壳，先验证“谁会用、为什么反复用、是否愿意分享或付费”。** 若要尝试商业化，应优先转向用户自有素材的青少年/业余球队、校园赛事、社群纪念卡，而不是继续扩大真实 NBA 素材库。

### 工程进度更新（同日）

- Claude 完成的 `app.js` 初步拆分已复核。目录和 `app-core.js` late-binding 思路可用，但交付状态曾包含模块语法错误、重复声明、缺少导入和向 imported binding 赋值等运行时问题；现已逐项修复，15 个应用模块全部通过 ES Module 语法检查，浏览器实测无 console error/warn。
- 3D 引擎已从 1,080 行自启动脚本抽为本地 workspace 包 `@card-builder/renderer`。核心包不再查询固定 DOM 或写入全局变量，提供 `setState`、`setView`、`resize`、`rebuild`、`captureCanvas`、`getHoverTiltState`、`destroy` 等显式 API；根目录适配器继续保留 `window.cardBuilderThree` 兼容面。
- 新增渲染状态归一化、3 项 Node 单元测试与 8 条 Playwright 浏览器 E2E 主流程；`npm run check` 现覆盖 21 个 ES Module，而不再只检查旧 `app.js`。
- 原 1,021 行的 `export.js` 已拆为 21 行兼容门面、746 行 Canvas 卡牌渲染、239 行特效画师与 89 行导出工作流。原认知复杂度 103 的 `drawExportEffect` 现仅负责状态分发，各特效画师互相隔离。
- 8 种导出特效均已建立 Chromium RGBA 像素 SHA-256 基线；共享卡牌 API 的卡牌校验、摘要投影、缩略图解析、token 哈希与路由解析也已收敛至单一核心，并由 6 项契约测试覆盖（含本地与 Vercel 直连/重写路径）。
- CSS 已完成第一轮保守收敛：删除共享库 v1/v2 Tab、全局 reduced-motion、≤560px/≤700px 工具按钮三组确定性重复覆盖，`styles.css` 由 8,034 行降至 7,970 行；新增无依赖层叠审计以阻止这三类回归。仍保留版本化 Pack/3D 视觉区块，避免以行数为目标破坏成品效果。
- 浏览器回归确认：3D 初始化状态为 `ACRYLIC / PBR`，Canvas 1440×1264，正反翻面正常，2400×3200 当前视角 PNG 成功生成，干净控制台。
- 此更新提高了工程边界清晰度，但没有改变产品决策：缺少真实用户、留存、付费和素材授权证据，仍是是否继续产品化的首要门槛。

## 2. 事实、判断与假设边界

### 已核验事实

- 当前前端包含 6 个卡片系列、8 个动态特效、7 类卡壳、正反面编辑、高清导出、3D 预览、本地/共享卡库、拆包、对比、成就、签名和闪光蒙版。
- 精选内容为 54 张人工影像卡，球员数据库为 28 人；媒体审计仍显示 `portraitVerified: 0/28`，不能把整个素材库表述为“已完成权利核验”。
- 迁移前 `app.js` 为 5,198 行、`styles.css` 为 8,034 行；前端主入口现已拆为 18 个领域模块，旧 `app.js` 仅保留作迁移对照。现有 3 项渲染器配置单测和 8 条浏览器 E2E 主流程，覆盖启动、导航、编辑、翻面、导出、卡库、共享 API 与拆包闭环。
- 导出职责已拆分为兼容门面、Canvas 卡牌渲染、特效画师和工作流；Vercel handler 认知复杂度 48、本地 `handleApi` 认知复杂度 41，双份 API 仍是当前最主要的维护热点。下一步应为特效增加像素快照或图像哈希测试。
- 修改前 390×844 页面把三个编辑面板同时展开，文档高度约 5,531px；本轮改成三阶段后，设计/球员/导出页面分别约 3,264 / 2,427 / 1,800px，并保持无横向溢出。
- GitHub `main` 当前远端 HEAD 为 `b8d3f20`，最近一次 Pages workflow 成功；Vercel 首页与 `/api/health`、GitHub Pages、Netlify 均返回 HTTP 200。Vercel health 返回 `storage: vercel-blob`。

### 审计判断

- 产品最强资产是“实时 3D 收藏品体验”，不是字段数量或素材数量。
- 目前功能广度已经超过信息架构和测试能力，继续横向加功能会降低整体质量。
- 收藏、拆包、稀有度和卡壳形成了统一的产品语言，但“制作工具”与“收藏游戏”两个目标仍在争夺首屏注意力。
- 商业价值无法由代码完成度推导；在没有真实用户行为数据前，任何增长或付费判断都只能是待验证假设。

### 尚未验证的假设

- 体育迷愿意花时间从零设计，而不是直接套模板。
- 拆包和收藏能带来复访，而不只是首次演示的新鲜感。
- 用户愿意公开分享作品，且能够提供拥有充分权利的素材。
- 用户愿意为高清导出、批量模板、实体打印或团队协作付费。

## 4. 产品与竞品分析

通用设计工具已经把“模板 + 上传图片 + 快速导出”做成标准能力。Adobe Express 的官方卡片工具强调免费模板、无需设计经验和 PDF/JPG/PNG 下载，这意味着 Card Builder 若只强调“做一张卡”，会直接进入大型通用工具的优势区间。[Adobe Express Card Maker](https://www.adobe.com/express/create/card)

Card Builder 的差异化更接近收藏体验：Topps 官方收藏指南把 base/parallel、拆包揭示和收藏社群作为核心语言，这与本项目的稀有度、卡壳、pack reveal 和收藏库高度一致。[Topps Collecting Guide](https://www-next.topps.com/pages/start-collecting-topps)

因此更合理的价值主张是：

> **把自己的体育时刻做成可旋转、可封装、可收藏的 3D 数字卡。**

这比“DIY 3D Making Card Studio”更清楚地回答用户收益，也自然支持三类目标用户：

1. 青少年/业余球队家长与教练：用自有比赛照片做赛季纪念卡。
2. 体育内容创作者：快速制作可分享的视觉内容。
3. 设计/技术招聘方：体验一个高完成度的 WebGL/Canvas 作品。

不建议当前同时服务职业球星收藏者、卡牌设计师、普通球迷、实体印刷用户和交易社区；这会让产品边界持续膨胀。

## 5. UI / UX 审核

### 做得好的地方

- 深色工作台把预览放在视觉中心，卡片质感、层级与品牌风格统一。
- 操作结果即时反馈，适合视觉探索；卡片旋转、翻面、导出和拆包形成“做完即可玩”的闭环。
- 桌面端 900px 预览区与 380px inspector 分工明确，浏览器控制台实测无报错。
- 移动端没有横向溢出，关键预览控制本轮统一到 44×44px。

### 主要问题

- **P0：首次任务不够明确。** 用户看到大量风格、特效、收藏和拆包入口，但不知道完成一张卡的最短路径。
- **P0：设计面板仍然偏长。** 三阶段解决了总体长度，设计阶段内部仍有系列、特效、闪光、稀有度、卡壳、照片、球队、徽章等多组设置。
- **P1：小字号过多。** 大量 7–9px 的装饰/元数据文本在普通笔记本和手机上可读性偏弱。
- **P1：核心动作层级分散。** “保存到卡库”“保存到本机”“下载项目”“PNG 导出”“发布共享库”含义接近，但分布在不同区域。
- **P2：收藏游戏会抢走编辑任务。** 拆包和 PK 很吸引眼球，但对首次制卡属于旁路行为。

### 本轮已实施

- 恢复“01 卡面设计 → 02 球员资料 → 03 保存导出”导航，只展示当前阶段。
- Tab 支持点击、左右方向键、Home、End，并同步 `aria-selected`、`tabindex` 与 panel `hidden`。
- 快速球员区退出长期 sticky，阶段导航在面板标题下保持 sticky，降低移动端固定区域占用。
- 卡牌库关闭时启用 `inert`，打开时自动聚焦关闭按钮，关闭后返回原触发控件。
- 移动端缩放、旋转、Motion、Flip、Reset 控件提升到 44px。
- 产品内和 README 增加非官方定位与素材权利提醒。

## 6. 代码与架构审核

### 优点

- 原生 JS/Canvas/Three.js 让核心渲染逻辑可见，作品技术含量真实，不依赖大型 UI 框架包装。
- 本地库、IndexedDB 图像恢复、Vercel Blob 共享库、导入导出与内容迁移组成了完整数据生命周期。
- 有 CSP、安全响应头、媒体授权闸门、数据审计和共享 API smoke test，不是只有视觉 demo。
- `prefers-reduced-motion`、显式 Toast 状态和失败回退说明开发过程考虑了异常场景。

### 风险与改进顺序

#### 已完成 P0：建立真实浏览器回归测试

已用 Playwright 建立 8 条可复现流程：打开编辑器/3D 预览、三阶段键盘导航、样式与特效选择、正反翻面、PNG 下载、本地卡库、共享库 health/加载、拆包翻开并关闭。它们能捕获主要的隐藏面板、事件绑定、下载与状态回归；后续仍应补充上传自有图片、球员/影像切换、移动视口与模态焦点陷阱。

#### 已完成 P0：拆分导出渲染热点

原 `drawExportEffect` 认知复杂度为 103，现已按 effect 拆成独立画师映射，并与 Canvas 卡牌绘制、下载/卡壳工作流解耦。8 种特效已通过 Chromium 导出 PNG 的 RGBA 像素 SHA-256 基线锁定；升级 Chromium、字体或有意调整视觉时，必须审阅并显式更新基线。

#### 已完成 P1：合并本地与 Vercel API 契约核心

`server/shared-server.mjs` 与 `api/[...route].js` 现共享发布校验、序列化、缩略图解析、token 鉴权、列表排序、球员筛选和直连/重写路由解析，显著降低行为漂移。文件系统/Vercel Blob、响应对象、媒体上传和管理员审计仍因运行环境不同保留在适配层，避免将部署依赖耦合进本地服务。

#### 已完成基础阶段：按领域拆分 `app.js`

主入口已拆为 18 个 ES Module，并以 `app-core.js` late-binding 解决循环依赖；3D 引擎另行抽为 workspace 包。E2E 已锁定 8 条关键业务行为，导出热点也已拆分；下一步不应再为了“文件更小”机械拆分，应处理本地/云端 API 重复、CSS 层叠热点和视觉快照测试。

#### 已完成第一轮 P1：收敛 CSS 层叠

已将 `styles.css` 从 8,034 行收敛至 7,970 行，删除三组可证明被后续规则完整覆盖的 CSS：共享卡库 v1/v2 Tab、全局 reduced-motion 和 ≤560px/≤700px 工具按钮尺寸。`npm run audit:css` 会解析规则并防止这三组覆盖重现。其余多个版本区块多为基础样式加视觉增量（尤其 Pack reveal 与 3D slab），不应为追求行数机械合并。下一轮如需继续，应先按领域拆文件并用视觉回归覆盖各区块，而不是直接删除同名选择器。

#### P2：优化自动建库循环

`autoBuildLibrary` 在循环中包含线性查找，数据规模扩大后可能退化。当前 54 张规模不是性能瓶颈，可在其他 P0/P1 完成后改为 Map 索引。

## 7. 素材、品牌与公开发布风险

NBA 官方条款明确将球队名称、Logo、比赛照片等视为受保护内容，并限制未经许可的复制、修改、公开或商业使用；人物图片还可能涉及隐私与肖像/公开权。该风险不能通过“非官方”声明自动消除，声明只用于减少误导，并不构成授权。[NBA Terms of Use](https://www.nba.com/termsofuse)

建议：

- README 和 UI 保留本轮新增的非官方/权利提示。
- `review_required` 素材不进入对外商业展示、模板或默认卡包。
- 公共版本优先使用原创虚构球员、明确授权照片或用户自有素材。
- 若继续真实职业体育方向，在变现、推广或扩大公开素材前取得专业法律意见。
- 不把“来源已记录”表述成“版权已授权”；这两者不是同一件事。

## 8. 是否继续：阶段门槛

建议给项目 **2–3 周封顶周期**，不再新增视觉特效，完成下列验证：

1. 找 10–15 位目标用户（业余球队家长/教练、体育内容创作者、卡牌爱好者）做任务测试。
2. 至少 60% 的测试者无需讲解即可完成“上传自有照片 → 编辑 → 保存/导出”。
3. 首次成功导出的中位时间低于 5 分钟。
4. 至少 3 人在 7 天内主动第二次使用，或明确愿意为高清/批量/打印支付。
5. 公共默认素材全部具有明确可说明的授权状态。

### 满足 4 项以上

继续做，但转入明确细分市场；下一阶段只做模板、批量生成、分享页和可选打印对接，不继续堆特效。

### 满足 2–3 项

保留为旗舰作品集，完成测试和架构收尾后冻结；把时间投入一个能展示账号系统、多人协作、AI/数据流程或商业指标的新项目。

### 满足 0–1 项

停止产品化投入。保留在线 demo、案例拆解、技术文章和审计报告，把 Card Builder 当作完成度很高的技术作品，而不是失败的创业产品。

## 9. 推荐路线图

### 接下来 1 周

- 固化 8 条浏览器 E2E 主路径，并补充上传自有图片、球员/影像切换与移动视口测试。
- 增加一个 3 步首次引导和“使用示例项目”。
- 把编辑区默认展开项减少到系列、照片、颜色；高级特效折叠。
- 建立匿名、需同意的最小漏斗：打开 → 开始编辑 → 上传 → 保存 → 导出。

### 第 2–3 周

- 完成 10–15 人可用性测试并记录成功率、用时和阻塞点。
- 在 CI 中固定 Chromium/字体版本运行特效像素哈希，并为本地与 Vercel 各自增加同一组 API 合约集成测试。
- 将公共演示素材替换为明确可发布内容。
- 根据验证结果决定“继续细分商业化”或“作品集冻结”。

## 10. 最终建议

**不要放弃这个项目，也不要继续无边界地做。**

它已经足以成为作品集中的主项目；继续增加第 9 种特效、第 8 种卡壳或更多 NBA 卡，对求职说服力和商业确定性的边际收益都很低。下一轮投入必须购买新的证据：真实用户是否完成、是否复用、是否愿意分享/付费，以及素材是否可合法公开。若这些证据没有出现，就应冻结 Card Builder，并选择一个能补足多用户、后端架构或 AI/数据能力的新项目。
